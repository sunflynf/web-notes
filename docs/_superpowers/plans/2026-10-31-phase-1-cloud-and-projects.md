# Phase 1: Cloud building blocks and Projects section Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild `docs/cloud-computing/` around eight building-block pages behind an architecture-map entry page, and move Projects to its own section at `/projects/`, without losing content or breaking any link.

**Architecture:**
- Content is MDX in the default docs instance.
- Projects moves to a second `plugin-content-docs` instance.
- All redirects live in one typed list (`redirects.ts`), which the config and a check script share.
- The architecture map is a small React component, `LayerFlow`, that renders `@docusaurus/Link`s, so the build checks its links. Phase 2 reuses it.
- Decision charts are Mermaid. A check script verifies the in-page click targets in each chart.

**Tech Stack:**
- Docusaurus 3.10.2 (classic preset, Rspack)
- React 19, TypeScript 7 (`yarn typecheck`)
- `@docusaurus/theme-mermaid`, `@theme/Tabs`, `@docusaurus/plugin-client-redirects`
- Node 24, which runs `.ts` imports natively, so the check scripts are plain Node with no new dependencies

**Spec:** `docs/_superpowers/specs/2026-10-31-cloud-and-technologies-reorg-design.md` (Phase 1 = sections 1.1–1.4, "Visuals", "Release and validation").

## Block page contract (Tasks 4–9 follow this; `cloud-blocks.mjs` enforces it)

**Frontmatter:** `title`, `sidebar_label`, `sidebar_position`, `description`. Positions:

| Page | `sidebar_position` |
|---|---|
| foundations | 1 |
| identity | 2 |
| compute | 3 |
| storage | 4 |
| databases | 5 |
| networking | 6 |
| messaging | 7 |
| monitoring | 8 |

**Body for every block except Foundations:** an `# <Title>`, then a one-line paragraph, then these H2s, exactly and in this order:

1. **`## Decision chart`**
   - Contains one ```` ```mermaid ```` `flowchart TD`.
   - Every end box that names a service has a line `click <NodeId> "#<id>"`.
   - Every such `<id>` must be an explicit heading id on the same page.
2. **`## Compare the options`**
   - One table with the columns `Option | You manage | Scales | Cost shape | AWS | Azure | GCP`.
3. **`## Set it up on AWS`**
   - One H3 per service, written as `### <Service> {#<id>}`.
   - **Full service:**
     - directly under the H3: `<Tabs groupId="aws-setup">` with exactly three `<TabItem>`s, `value="console"`, `value="cli"` and `value="terraform"`, labelled Console, CLI and Terraform;
     - numbered steps;
     - each gotcha as a `:::caution` admonition right under the step it belongs to.
   - **Short service:** 3–6 bullet notes, no tabs.
4. **`## Connects to`**
   - At least 3 links.
   - At least one goes to another block page, and at least one goes to a note outside `docs/cloud-computing/`.

**Body for Foundations (*my call*, the spec gives it no services):** H2s `## Core ideas`, `## Pricing`, `## Set up the AWS CLI`, `## Azure and GCP quick reference` and `## Connects to`, in that order. No chart.

**Required service ids:**

| networking | `vpc`, `cloudfront` | `route53` |

  export type LayerFlowProps = {
